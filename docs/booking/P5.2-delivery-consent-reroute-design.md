## 1. The correctness core — per-offset delivery ledger (replaces `reminder_sent_at`)

**Why `reminder_sent_at` is insufficient.** It is a single boolean-ish timestamp on the appointment:
one reminder, one channel, and reschedule handling is the coarse "clear it to re-fire" hack (P2.4).
It cannot express *"the 24h email fired but the 24h SMS didn't,"* nor *"after reschedule, fire the
new-time reminders once each — even if the new time equals a prior time."*

**Design.** A per-(appointment, schedule_version, event, offset, channel) delivery record. The unique
constraint IS the fire-once guarantee; `schedule_version` (a monotonic counter bumped on every
reschedule) ties each delivery to a specific scheduled instant so re-anchoring is correct and
idempotent.

- **`appointments.schedule_version int not null default 1`** — the shared reschedule mover
  (`rescheduleAppointment`) bumps it (`schedule_version + 1`) in the same atomic move UPDATE.
- **`booking_notification_deliveries`** — one row per delivered notice:
  `(appointment_id, schedule_version, event, offset_minutes, channel)` **UNIQUE** = fire-once.
  `offset_minutes = 0` for immediate events (confirmation/rescheduled/cancellation); the reminder
  offsets (e.g. 1440 = 24h) for reminders. `status` records sent/deferred/blocked/failed;
  `comm_message_id` links the actual send.
- **`booking_reminder_config`** — which offsets fire, per channel; **`sms_enabled` default false is
  the P5 feature flag**; values carry `is_assumption` (config default — verify, §4.3).

**Claim-then-send (preserves fire-once + defer-retry, now per offset/channel/version):**
1. The reminder job scans scheduled appts at their **current** `schedule_version`; for each configured
   `(offset, channel)` that is DUE (`now ∈ [starts_at − offset, starts_at]`):
2. **Claim:** `INSERT … (appt, version, 'reminder', offset, channel, status='sent') ON CONFLICT DO
   NOTHING RETURNING id`. No row → already delivered → skip (fire-once). This is the atomic claim,
   replacing the `reminder_sent_at` null→now flip.
3. **Send** the claimed leg via `sendAppointmentNotice` → `sendThroughGate`.
4. On **defer/block** (quiet hours, template-not-approved, transient): **DELETE the claim** so a later
   in-hours tick re-claims and retries (mirrors today's `reminder_sent_at=null` release). On success:
   keep the row + set `comm_message_id`.

**Reschedule survival:** a reschedule bumps `schedule_version` → the new time's `(offset, channel)`
reminders have **no** delivery row for the new version → they fire once each for the new time; old
version rows are inert (the job only queries the current version). Correct even if rescheduled back
to a previously-used time (the version differs). **`reminder_sent_at` is retired** by this ledger
(kept as a nullable column for one release for rollback safety, then dropped).

### Migration 093 (forward-only — OWNER APPLIES; shown, not run)

```sql
-- 093_booking_notification_deliveries.sql
-- Per-offset/channel delivery ledger + reschedule schedule_version + reminder config (P5). The
-- ledger's UNIQUE key is the fire-once guarantee; schedule_version makes reschedule re-anchoring
-- correct. Additive + forward-only. No app path depends on it until the P5 email-lifecycle slice
-- ships. reminder_sent_at is retained (nullable) for one release for rollback, then removed.

alter table appointments add column if not exists schedule_version int not null default 1;

create table if not exists booking_notification_deliveries (
  id              uuid primary key default gen_random_uuid(),
  appointment_id  uuid not null references appointments(id) on delete cascade,
  schedule_version int not null,
  event           text not null check (event in ('confirmation','reminder','rescheduled','cancellation')),
  offset_minutes  int  not null default 0,   -- reminders: minutes-before-start; 0 = immediate events
  channel         text not null check (channel in ('email','sms')),
  status          text not null default 'sent' check (status in ('sent','deferred','blocked','failed')),
  comm_message_id uuid references comm_messages(id) on delete set null,
  created_at      timestamptz not null default now(),
  unique (appointment_id, schedule_version, event, offset_minutes, channel)
);
create index if not exists idx_appt_notif_deliv_appt
  on booking_notification_deliveries (appointment_id, schedule_version);

create table if not exists booking_reminder_config (
  id            text primary key default 'global',
  offsets_minutes int[] not null default '{1440}',   -- 24h; e.g. '{1440,60}' adds a 1h reminder
  email_enabled boolean not null default true,
  sms_enabled   boolean not null default false,        -- P5 SMS feature flag (OFF until Stage 4)
  is_assumption boolean not null default true,          -- config default — verify (§4.3)
  updated_at    timestamptz not null default now()
);
insert into booking_reminder_config (id) values ('global') on conflict do nothing;

-- RLS: default-deny; writes run service-role AFTER the rbac assertion (same pattern as the booking
-- config tables in mig 069). Staff read.
alter table booking_notification_deliveries enable row level security;
alter table booking_reminder_config             enable row level security;
drop policy if exists and_read on booking_notification_deliveries;
create policy and_read on booking_notification_deliveries for select using (
  is_super() or has_role('fsa') or has_role('licensed_staff') or has_role('admin')
  or has_role('compliance') or has_role('supervisor')
);
drop policy if exists brc_read on booking_reminder_config;
create policy brc_read on booking_reminder_config for select using (
  is_super() or has_role('fsa') or has_role('licensed_staff') or has_role('admin')
  or has_role('compliance') or has_role('supervisor')
);

-- Rollback: drop the two tables + `alter table appointments drop column schedule_version;`
```

**Apply-time note (for deploy-notes on approval):** additive, forward-only; safe on the small table.
Apply via the repo migration workflow (not from this environment). The P5 email-lifecycle slice is
gated on this migration being applied.

## 2. SMS consent capture surface + evidence (Stage 3 — before any Stage 4 send)

**No SMS is sent until consent capture is built AND verified.** Capture is Stage 3; sends are Stage 4.

- **Surface (public booking form):** a **separate, affirmative, UNCHECKED** SMS opt-in checkbox +
  disclosure (approx: *"Text me appointment reminders at this number. Msg & data rates may apply.
  Reply STOP to opt out, HELP for help."*). Phone becomes required iff checked. **Independent of the
  email opt-in; never pre-checked; never inferred.**
- **Persistence (mirrors the email pattern in `book.ts`):** on booking with the box checked, write a
  `consent_intent` activity `channel:'sms'`, `scope:'booking'`, `SMS_CONSENT_DISCLOSURE_VERSION` +
  `consent.captured` audit `channel:'sms'`. Contact-level evidence (bookers are contacts), reflected
  into `consents(member,'sms','granted')` when a member mapping exists (**D-P5-1**). **No schema
  change** — reuses `activities`/`consents`/`contact-consent.ts`.
- **Read at send time:** the gate (step 2) resolves SMS consent from this evidence via
  `contact-consent.ts` — a **real** consent signal, NOT the email path's transactional waiver.
- **STOP/START:** inbound STOP (`keywords.ts`) revokes + DNCs the contact key; instant, blocks later
  SMS legs at gate step 2/5.
- **Verification gate:** Stage 4 SMS enablement is blocked until the capture writes verified evidence
  the gate actually reads (a test proving capture→gate-consent round-trips).

## 3. Lifecycle reroute — stop calling `sendBookingConfirmation` directly

**New single entry:** `sendAppointmentNotice(appointmentId, event, opts)` (extends `notify.ts`, does
NOT touch `personalize.ts`). It: resolves the recipient + channels (email if email-consent; SMS iff
`booking_reminder_config.sms_enabled` + SMS consent + A2P live), consults the **delivery ledger**
(fire-once per event/offset/channel/version), renders the **approved template for that event×channel**,
sends via `sendThroughGate`, and records the delivery. One lifecycle path; the gate is unchanged.

**Reroute the four call sites (each a later diff):**

| Call site | Today | P5 |
|---|---|---|
| `book.ts:254` | `sendBookingConfirmation` | `sendAppointmentNotice(id,'confirmation')` |
| `manage.ts:203` (reschedule) | `sendBookingConfirmation` | **`sendAppointmentNotice(id,'rescheduled')`** ← reclassification |
| `manage.ts:110` (cancel) | `sendCancellationNotice` | `sendAppointmentNotice(id,'cancellation')` |
| `/api/app/appointments/[id]/send` | `sendBookingConfirmation` | `sendAppointmentNotice(id, <event>)` via the classifier |

`sendBookingConfirmation`/`sendCancellationNotice` become thin wrappers over
`sendAppointmentNotice` (or are removed) — a **reschedule is a `rescheduled` event**, never a fresh
"you're booked" confirmation. The public reschedule flow (`/api/public/booking/manage`) is covered
because it calls the same `rescheduleAppointment` mover.
