# P5.3 — SMS Consent Capture Surface + Evidence (DESIGN)

> **Design only — no send code.** Stage 3 lands the capture + evidence + read-path and is **verified
> before any Stage 4 SMS send**. Mirrors the existing EMAIL booking-consent pattern (`book.ts`); adds
> no schema (reuses `activities`/`consents`/`contact-consent.ts`). Loaded via `twilio-a2p-compliance`.

## Implementation reconciliation (Stage 3 as built — supersedes the store choices below)
Building Stage 3 surfaced the **existing** contact-resolvable SMS consent store, so the capture
was wired to it rather than the `activities`/`consents` sketch below (architecture preservation,
§6 — one SMS-consent path, not a second):
- **Read-path + evidence store = `comm_contact_consents` (mig 074)** — the SAME store the public
  contact form writes, STOP/HELP mutate, and the gate already reads at send time
  (`send.ts → durableContactConsentGranted`, `channel='sms'` + `contact ILIKE %<last-10>`,
  newest-wins). Booking writes a durable `action='granted'` row there; nothing new to wire for the
  gate to resolve it in Stage 4. **Not** a new `activities(consent_intent,'sms')` read-path.
- **Disclosure + version = the registered A2P program `SMS_CONSENT` + `smsConsentVersion()`**
  (content-derived hash), reused verbatim — it already enumerates "appointment scheduling and
  reminders," so booking consents to the ONE registered customer-care program, not a parallel
  `sms-booking-v1` campaign (twilio-a2p-compliance: one registered A2P program).
- **Evidence-of-record** is the `comm_contact_consents` row itself (first-class `consent_text` /
  `consent_version` / `source_url` / `ip_address` / `user_agent` / `captured_at`), **mirrored** to
  the append-only `audit_log` `consent.captured` (phone as last-4 only). Both halves of §2a are met.
- **Member reflection not needed at booking:** `comm_contact_consents` is contact-keyed and the
  gate reads it directly; a member-keyed `consents` row materializes on lead→member conversion via
  the existing WF-1 pathway, not at capture. (D-P5-1 resolved: contact-level primary, as built.)
- **Capture surface:** a separate, affirmative, default-UNCHECKED checkbox on the booking details
  step; the label is `SMS_CONSENT.disclosure` **verbatim** (shown text == stored evidence, no
  drift). Phone becomes required + must be ≥10 digits **iff** checked (`PublicBookingInput`
  superRefine) — no consent row without a real number. **No SMS is sent** (Stage 4, behind
  `booking_reminder_config.sms_enabled=false`). Proof: `tests/booking-sms-consent.test.mjs`
  (capture→gate round-trip + STOP/START + fail-closed + schema, 12 assertions).

## Principle
SMS requires **explicit, affirmative, unchecked TCPA prior-express-written consent**, captured at the
point of booking, **independent of the email opt-in and never inferred from it**, re-checked fresh by
the gate at send time, and **instantly revocable by STOP**. Until the evidence a real send would read
is proven present, **no SMS is sent** (Stage 4 is gated on Stage 3 verification).

## 1. Capture surface + EXACT disclosure language (public booking form)
- A **separate checkbox, default UNCHECKED**, on the details step. The **exact** label text
  (`SMS_CONSENT_DISCLOSURE_VERSION = 'sms-booking-v1'`), rendered verbatim next to the checkbox:
  > ☐ **Text me about this appointment.** By checking this box, I agree to receive automated text
  > messages (appointment confirmations, reminders, and schedule changes) from **[FSA practice name]**
  > at the mobile number I provide. Consent is **not** a condition of booking. Message frequency
  > varies; **message & data rates may apply**. Reply **STOP** to cancel, **HELP** for help.
  >
  > *(The bracketed practice name resolves from `site.ts` CONTACT at render — a real value, never a
  > placeholder; if unresolved the checkbox is not shown.)*
- **Phone becomes required iff the box is checked** (Zod refine: `sms_opt_in === true ⇒ phone present
  + valid E.164-normalizable`). Unchecked → phone optional, **no SMS evidence written**.
- **Independent of the email opt-in** — no shared state, never pre-checked, never defaulted from
  email. Email consent and SMS consent are captured and stored separately.
- The exact text + its version are **persisted with the evidence** (§2a) so the precise wording shown
  at consent time is reproducible for any dispute, even after the copy is later revised.

## 2. Evidence persistence (`book.ts`, mirrors the email pattern)
On a booking whose payload carries `sms_opt_in: true` (validated + phone present):
- Write an **`activities`** row: `kind:'consent_intent'`, `entity_type:'contact'`,
  `entity_id:<contact_id>`, `channel:'sms'`, `scope:'booking'`, note referencing
  `SMS_CONSENT_DISCLOSURE_VERSION` and the captured number tail.
- Write an **`audit_log`** row: `action:'consent.captured'`, `entity:'contact'`,
  `diff:{channel:'sms', scope:'booking', version:…}`.
- **D-P5-1 (recommended):** the contact-level `consent_intent(sms)` is the **primary** evidence
  (bookers are contacts). When the contact maps to a `household_member`, ALSO upsert
  `consents(member_id,'sms','granted')` so the member-keyed gate path sees it (`ON CONFLICT
  (member_id, channel)` — the full unique constraint stays the arbiter; never a partial index).
- **No new table.** Evidence lives in the same stores STOP/START already mutate.

## 2a. Consent evidence record (TCPA defensibility) — the immutable proof
The **`audit_log`** row is the defensible record of consent (append-only + tamper-locked, mig 077).
On capture, `consent.captured` writes a **structured `diff`** carrying everything a TCPA dispute needs
to reconstruct *who agreed to what, when, and exactly what they saw*:

| Field | Value | Purpose |
|---|---|---|
| `channel` | `'sms'` | which channel was consented |
| `granted_at` | the audit row's `at` (server timestamp) | **WHEN** |
| `method` / `source` | `'web_booking_form'` | **WHERE/HOW** (the capture surface) |
| `contact_id` (entity_id) | the booker's contact | **WHO** |
| `phone_tail` | last 4 of the E.164 number | which number (no full PII in the log) |
| `disclosure_version` | `'sms-booking-v1'` | the versioned copy identifier |
| `disclosure_text` | the **exact string shown** (verbatim) | **WHAT THEY SAW** — reproducible verbatim |
| `consent_action` | `'granted'` | grant vs revoke |

Because `audit_log` is append-only and cannot be UPDATE/DELETE'd (mig 077 lockdown), this row is the
tamper-evident proof. The parallel `activities(consent_intent, channel:'sms')` row carries the same
`disclosure_version` and is the **read-path** consent-state (what the gate resolves); the audit row is
the **evidence-of-record**. Revocation writes a matching `consent.revoked` audit row (STOP), so the
full grant→revoke history is reconstructable. *(Alternative considered: a dedicated
`booking_sms_consent_events` table like `workshop_consent_events` — offers a first-class structured
store but is a schema change; the immutable-audit approach meets TCPA defensibility with no migration.
**D-P5-5: audit-record vs dedicated table — recommend audit-record.**)*

## 3. Read at send time (gate step 2 — Stage 4 wiring, not built here)
- The SMS leg resolves consent from this evidence via `contact-consent.ts`
  (`latestConsentGranted`/`consentContactKey`/`smsTail`) → a **real** consent input to
  `evaluateGate` step 2. It is **NOT** the email path's transactional `consentWaived`/
  `durableConsentGranted` — SMS consent is affirmative, never waived.
- An opt-out **always wins**: a `consents.status='revoked'` / DNC / STOP row makes the gate block the
  SMS leg regardless of a prior `consent_intent`.

## 4. STOP / revocation → suppression → honored on the NEXT send
The revocation path already exists (`keywords.ts` → `inbound.ts`) and P5 reuses it unchanged:
1. Inbound **STOP** (verified Twilio webhook) → **writes suppression**: upserts
   `consents(member/contact,'sms','revoked')` **and** inserts a `dnc_entries` row for the number,
   plus a `consent.revoked` audit row (the revocation half of the evidence trail). Instant.
2. **Honored on the very next send because the gate reads FRESH at send time** (the whole point of
   `sendThroughGate` re-resolving context per send): the next `sendAppointmentNotice` SMS leg is
   blocked at **gate step 2 (consent revoked)** and/or **step 5 (DNC)** — the send never dispatches;
   it is logged + (for an escalating step) surfaced, never silently dropped. There is **no cached
   consent** that could let a post-STOP send slip through.
3. **START** re-grants (a fresh `consent.captured`); **HELP** replies help text, no consent change.
4. Because capture keys evidence by the same contact/number the inbound path mutates (`smsTail`/
   `consentContactKey`), STOP flows straight through — **no separate booking opt-out list**, one
   suppression source of truth.

**Delivery-ledger interaction:** a blocked SMS leg records `status:'blocked'` in
`booking_notification_deliveries` (not `'sent'`), so a post-STOP reminder is marked handled-and-blocked
for that (version, offset, channel) — it does not retry into a suppressed number.

## 5. Verification gate (why Stage 4 can't jump ahead)
Stage 3 is "done" only when a test proves the **capture → gate-consent round-trip**: given a booking
with `sms_opt_in`, the written evidence makes `evaluateGate` step 2 return "consent present" for that
contact's SMS channel, and a STOP flips it to blocked. Until that passes, `booking_reminder_config.
sms_enabled` stays **false** and no SMS leg is wired.

## 6. TRAIGA (D-P5-3 — needs your call)
Booking SMS are **transactional, human-authored approved templates** (not AI-generated), so the
TRAIGA *AI-disclosure* requirement arguably does not attach. The templates will still carry sender
identity + STOP/HELP. **Confirm** whether you want a TRAIGA AI-disclosure line on these transactional
notices anyway (conservative), or to treat them as out-of-scope for that specific requirement.

## 7. What Stage 3 builds (each a diff before commit)
